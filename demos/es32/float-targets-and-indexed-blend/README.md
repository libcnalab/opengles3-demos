# es32-float-targets-and-indexed-blend

Minimum version: **OpenGL ES 3.2** (shaders are `#version 320 es`). On an ES 3.1 implementation such as Mesa's softpipe the
executable reports `SKIP_UNSUPPORTED`.

Two ES 3.2 features that only make sense together. A floating-point color buffer exists to hold values that an 8-bit buffer
would clip, and blending is the operation that most often pushes a value outside [0, 1]. ES 3.2 also lets every draw buffer of one
framebuffer have its own blend state, so that one draw can accumulate light additively into an HDR buffer, composite with alpha
into another and simply overwrite a third.

## What it shows

**Float color targets (ES 3.2 Table 8.10, section 9.4.3).** `R16F`, `RG16F`, `RGBA16F`, `R32F`, `RG32F`, `RGBA32F` and
`R11F_G11F_B10F` are color-renderable *and required* in core ES 3.2 (columns "CR" and "Req. rend."). In ES 3.0 and 3.1 they were color-renderable only with the
extension `EXT_color_buffer_float`. `RGB16F`, `RGB32F` and `RGB9_E5` are texture formats only: they are not color-renderable.
The demo renders a 16 x 16 pattern into each of the seven formats whose values are chosen to be exactly representable and mostly
outside [0, 1]: a red ladder of `+-1.5 * 2^(x-4)` (0.09375 ... 3072) with the sign alternating from row to row, a green ramp from
-4.875 to +4.375, a blue that is 3.75 on even rows and -2.5 on odd rows (HDR white and a negative), an alpha from 0.25 to 4.0.
Two probe texels hold the extremes of each format (65504 and -65504 for 16-bit floats, 2^100 and 1000000.5 for 32-bit floats,
65024 and the clamping of 100000 to 65024 / 64512 for the packed format) and a value that no format represents exactly (1.4).
Everything is read back with `glReadPixels(RGBA, FLOAT)`, the only format/type pair ES 3.2 accepts for a floating-point surface
(16.1.2). A float buffer rejects `RGBA / UNSIGNED_BYTE` with `INVALID_OPERATION` (16.1.3). Missing components read as 0, 0, 1; the
unsigned 11/10-bit floats turn negative values into zero (2.3.4.3, 2.3.4.4).

**Blending into float targets (15.1.5).** For a floating-point color buffer "no clamping occurs": source, destination and the blend
factors keep their values. The demo blends `SRC_ALPHA / ONE_MINUS_SRC_ALPHA` with a source alpha of 2.5 (factors +2.5 and -1.5) into
each of the seven formats and accumulates four additive draws of 3.75 into 15.0. There is one exception that the spec states
explicitly: *"An INVALID_OPERATION error is generated by any command that transfers vertices to the GL if blending is enabled and
any draw buffer has 32-bit floating-point format components."* `GL_EXT_float_blend` removes that error, so the expectation is
computed from `metagl::HasExtension("GL_EXT_float_blend")` and printed: with the extension the 32-bit targets must blend exactly like
the 16-bit ones, without it the draw must fail with `INVALID_OPERATION` and change nothing. All drivers in the test matrix expose the
extension, so only the first branch runs here; the second is implemented and documented but not exercised.

**HDR scene (the picture).** A perspective camera looks at a checkered floor with three boxes and two emissive spheres. Each sphere
is a point light with intensities up to 6; a sun and an ambient term complete a Lambert shading model whose results reach 12 at
the emissive spheres. Additive glow halos (`glBlendFunc(ONE, ONE)`, depth test on, depth writes off) are blended on top into the
RGBA16F target. The target is then shown twice side by side: the left half is `min(hdr, 1)`, what an RGBA8 target would hold (lamps
and highlights clip to flat white), the right half is Reinhard tone mapping `m / (1 + m)` with `m = 1.2 * hdr`.

**Indexed blend state (15.1.5, 15.2.2, 20.1).** One MRT framebuffer has four attachments in four different formats:
`RGBA8`, `RGBA16F`, `R11F_G11F_B10F` and `RGBA16F`. One fragment shader writes four uniform colors, one per draw buffer. The
per-draw-buffer commands `glEnablei`, `glDisablei`, `glBlendFunci`, `glBlendFuncSeparatei`, `glBlendEquationi`,
`glBlendEquationSeparatei` and `glColorMaski` give each buffer its own state; `glIsEnabledi`, `glGetIntegeri_v` and `glGetBooleani_v`
read it back. Ten scenarios are drawn (the first by `render()`, the others by `validate()`; each draw is four 32 x 32 quadrants with different destination and source colors, so every
buffer has 16 independent blend inputs per scenario): replace / additive / alpha-over / reverse-subtract on the four buffers;
a global state followed by indexed overrides of single fields; separate RGB and alpha factors and equations that differ on
every buffer; write masks with and without blending; enable flags per buffer where a disabled buffer keeps its functions;
constant-color factors; the non-indexed commands undoing per-buffer junk; `SRC_ALPHA_SATURATE` and `DST_ALPHA`
factors. The window shows the first scenario in its bottom strip.

## Central calls

`glEnablei` / `glDisablei` / `glIsEnabledi(BLEND, i)`, `glBlendFunci`, `glBlendFuncSeparatei`, `glBlendEquationi`,
`glBlendEquationSeparatei`, `glColorMaski`, `glGetIntegeri_v(BLEND_SRC_RGB ...)`, `glGetBooleani_v(COLOR_WRITEMASK)`, the
non-indexed `glEnable(BLEND)`, `glBlendFunc[Separate]`, `glBlendEquation[Separate]`, `glColorMask`, `glBlendColor`,
`glReadPixels(RGBA, FLOAT)`, `glTexStorage2D` / `glRenderbufferStorage` with the float formats, `glClearBufferfv`,
`glDrawBuffers`, `glGetFramebufferAttachmentParameteriv(COMPONENT_TYPE)`.

## Shader concepts

`pattern.frag` computes the exactly representable pattern from `gl_FragCoord` and swaps in two uniform probe values.
`outputs.frag` has four `layout(location = N)` outputs fed from a `uniform vec4 u_src[4]`: plain values, so that every
result in the buffers is decided by the fixed-function state and nothing else. `scene.frag` does the HDR lighting in `highp`
(`1 / (1 + d^2)` falloff, no clamping). `glow.vert` builds camera-facing billboards from `gl_VertexID`. `compose.frag` reads texels
with `texelFetch` (no filtering: `R32F` is not texture-filterable) and shows them: the scene as `min(hdr, 1)` | Reinhard, the float
textures through the signed curve `s / (1 + |s|) * 0.5 + 0.5` (0 maps to mid-grey), the RGBA8 panel as it is. `precision highp
sampler2D` is declared because the default sampler precision of fragment shaders is `lowp`.

## Expected image (256 x 256)

Top 160 rows: the scene; left of the two grey columns the 8-bit view, right the tone-mapped view. Middle 32 rows: seven swatches of
the float patterns (stripes: the R ladder, alternating rows: the sign; packed format: the negative rows are grey because they
were clamped to zero). Bottom 64 rows: four MRT panels with four quadrants each; the RGBA8 panel is the saturated replace result,
the other three show the additive, alpha-over and reverse-subtract results of the same draw through the signed curve.

## How it is validated

* **Float formats:** all seven formats are framebuffer complete as texture and as renderbuffer; `COMPONENT_TYPE` is `FLOAT`,
  `COLOR_ENCODING` is `LINEAR`, component sizes are at least the Table 8.10 bits (absent components 0); every one of the 256 x 4
  texels of each pattern equals the CPU model **exactly** (all values are representable; the only inexact probe, 1.4, is checked
  against the two neighbours the spec allows: 32-bit exactly, 11/10-bit "closest or toward zero", 16-bit within 2^-10 because the
  spec names no rounding rule). `glClearBufferfv(3.75, -2.5, 0.5, 2)` is read back from float renderbuffers (negative becomes 0 in the
  packed format). The implementation-chosen `IMPLEMENTATION_COLOR_READ_TYPE` must be one of the types that float buffers accept.
* **Negative controls:** the same pattern drawn into RGBA8 must *not* match the float model (about 1000 of 1024 components differ) and must
  match the model clamped to [0, 1]; the MRT results of the scenario with four different states must differ from what each
  neighbour's state would give (4 of 4 buffers), so the per-buffer comparison provably can fail.
* **Float blending:** exact results (6, -8, 0.5, 5.5 and 15, 2, 1, 4 and their stored forms per format); the 32-bit branch is selected
  from `GL_EXT_float_blend`.
* **Not color-renderable:** `RGB9_E5` and `RGB32F` textures give an incomplete framebuffer, the renderbuffers raise `INVALID_ENUM`;
  `RGB16F` is skipped (and reported) when `GL_EXT_color_buffer_half_float` makes it renderable.
* **MRT scenarios:** the CPU model implements Tables 15.1 and 15.2 per buffer: fixed-point buffers clamp source, destination,
  constant color and factors to [0, 1] and quantize to 8 bits; float buffers do not clamp; the packed format has no alpha (Ad = 1,
  negative results become 0); masked components keep their old value. The comparison covers all 4096 pixels of each buffer. 8-bit
  buffers use a tolerance of 2 steps (the same bound as `es20-blending`: blending in 8-bit fixed point rounds each factor product,
  the spec asks only for a precision no lower than the destination); float buffers use **zero** tolerance, which is legitimate
  because every product and sum in the scenario table is checked at start-up to be exactly representable (the demo throws a
  `Failure` otherwise). After every scenario the state of **all** `MAX_DRAW_BUFFERS` indices (not only 0..3) is read back with
  `glIsEnabledi`, `glGetIntegeri_v` and `glGetBooleani_v` and compared with the commands issued.
* **Non-indexed commands:** after a different indexed state on every index (0..MAX_DRAW_BUFFERS-1), each of `glEnable`, `glDisable`, `glBlendFunc`, `glBlendFuncSeparate`,
  `glBlendEquation`, `glBlendEquationSeparate` and `glColorMask` is shown to set its fields for every index and to leave every other
  field of every buffer alone; `glIsEnabled`, `glGetIntegerv(BLEND_*)` and `glGetBooleanv(COLOR_WRITEMASK)` report buffer zero.
* **Errors:** index = `MAX_DRAW_BUFFERS` (and 0xFFFFFFFF) gives `INVALID_VALUE` for `glEnablei`, `glDisablei`, `glIsEnabledi`,
  the four `glBlend*i` commands, `glColorMaski`, `glGetIntegeri_v` and `glGetBooleani_v`; `glIsEnabledi(DEPTH_TEST)` and
  `glGetIntegeri_v(DEPTH_FUNC)` give `INVALID_ENUM`; the rejected commands change no state.
* **HDR scene:** a small CPU ray tracer (plane, boxes, spheres, the same lighting formula, additive halos with the depth test)
  predicts the HDR value of every probe pixel. A pixel is used only when the same objects are seen at its centre and at eight points
  1.2 pixels around it, which excludes edges, tessellated silhouettes and checker borders (122 probes, 41 of them above 1.0). The
  tolerance is a sanity bound of 0.5 % + 2^-12: the spec gives no accuracy for interpolation and shader arithmetic, and the only
  defined error is the RGBA16F storage (2^-11 relative, here accumulated over up to three roundings: opaque value, two halos). The
  measured worst deviation is printed (1.84e-3 relative). The window pixels of the same probes are compared with `min(hdr, 1)`
  (left) and `m / (1 + m)` (right) within 1/255, and the swatches and MRT panels are compared with the signed curve.

## Pitfalls

* Blending into a **32-bit** float target without `GL_EXT_float_blend` is an error in core ES 3.2 (the extension is exposed
  everywhere in the matrix, so check it on a device before relying on it).
* A floating-point `glReadPixels` needs `RGBA / FLOAT`; `UNSIGNED_BYTE` is an `INVALID_OPERATION` there.
* `RGB16F` and `RGB32F` are texture formats; the framebuffer is incomplete (`RGB32F`) or complete only through
  `EXT_color_buffer_half_float` (`RGB16F`). Mesa answers `FRAMEBUFFER_UNSUPPORTED` for `RGB32F` where the spec says
  `FRAMEBUFFER_INCOMPLETE_ATTACHMENT`.
* Blend state is per *draw buffer index*, and in ES draw buffer i is `COLOR_ATTACHMENTi` or `NONE`. It is not per attachment object.
  Non-indexed commands overwrite the state of all draw buffers; `glIsEnabled(BLEND)` and `glGetIntegerv(BLEND_*)` describe buffer 0.
* The constant blend color is clamped only when the destination is fixed-point, so one `glBlendColor` can act differently on two
  buffers of the same draw.
* Dithering is initially enabled and changes 8-bit results by +-1; the demo disables it.
* The default sampler precision in a fragment shader is `lowp`; `texelFetch` of float textures needs `precision highp sampler2D`.

## Known driver deviations (kept as strict checks, labelled XFAIL on the named driver)

* **Mesa (all three Mesa drivers):** an `RGB32F` texture on `COLOR_ATTACHMENT0` gives `FRAMEBUFFER_UNSUPPORTED`; ES 3.2 9.4.1
  and 9.4.2 require `FRAMEBUFFER_INCOMPLETE_ATTACHMENT`.
* **radeonsi:** `glIsEnabled(BLEND)` returns TRUE only when blending is enabled for all draw buffers; ES 3.2 15.1.5.5 says it
  reports draw buffer zero.
* **zink (lavapipe):** with blending enabled and a write mask that masks G or B but writes R and A (e.g. `TFTT`), the masked
  channel is blended and stored (observed with the mask on all four buffers; masks such as `FTTT`, `TTTF`, `FFTT` and `FTFT` and
  every mask with blending off work). ES 3.2 15.2.2: masked components are not written.
