# Independent audit report: diagnostics and ES 2.0 foundations

Audited all 18 assigned demo directories against `AUDIT_BRIEF.md`, project validation/limitation
docs, and the local Khronos ES 3.0 / GLSL ES specifications. No source files were changed.

## Findings

### WEAK — `es20-textures-2d`

- [main.cpp:219](demos/es20-foundations/textures-2d/main.cpp:219), [README.md:47](demos/es20-foundations/textures-2d/README.md:47)
- The linear-filter CPU comparison hard-fails when any channel differs by more than 3/255. ES 3.0 §3.8.10.2 defines the linear-filter texel selection and weighted result (equation 3.22), but provides no minimum fractional precision that bounds this error. The README correctly calls filter precision implementation-dependent, but uses that as a reason for a hard threshold.
- **Fix:** keep the CPU result and measured error as diagnostics, but make the accuracy check non-failing unless a normative precision bound is available. Keep hard checks for the exact NEAREST cases, state, and texture contents.

### WEAK — `es20-mipmaps`

- [main.cpp:87](demos/es20-foundations/mipmaps/main.cpp:87), [main.cpp:205](demos/es20-foundations/mipmaps/main.cpp:205), [main.cpp:239](demos/es20-foundations/mipmaps/main.cpp:239), [README.md:117](demos/es20-foundations/mipmaps/README.md:117)
- The CPU comparisons impose 1/64 texel-weight and 1/16 LOD-weight error limits, while the README says ES 3.0 places no bound on the accuracy of λ or filter weights. ES 3.0 §3.8.10.1 permits an implementation to approximate ρ; §§3.8.10.2 and 3.8.10.4 give the ideal filtering equations but no corresponding minimum implementation precision. “Hardware uses” these fractional bits is not a normative guarantee.
- **Fix:** retain strict assertions only where the chosen coordinates are separated enough from LOD/texel boundaries to guarantee the same result under the allowed approximation. Report blend-weight/filter measurements without failing on an unbounded accuracy criterion.

### WEAK — `es20-mipmaps`

- [main.cpp:1152](demos/es20-foundations/mipmaps/main.cpp:1152), [README.md:85](demos/es20-foundations/mipmaps/README.md:85)
- The demo hard-checks that every generated level of a uniform base stays within one 8-bit step of the base color. ES 3.0 §3.8.10.5 requires a “filtered reduction” and explicitly does not prescribe a filter algorithm; the README acknowledges that constant-image preservation is an assumption beyond the literal text. This is an implementation-dependent result and cannot be a conformance hard check under the audit brief.
- **Fix:** print this result as an observation, or validate only the guaranteed generated level sizes, replaced-level range, base-level preservation, completeness, and defined errors.

## Clean demos

- `diagnostics-capabilities` — checked version-gated limit minima, extension enumeration, compressed-format requirements, and queried default-framebuffer values against the EGL config requested by the runtime.
- `es20-blending` — blend equations/factors and state are compared to the CPU model; tolerance is justified from fixed-point destination precision and conversion.
- `es20-clear-viewport-scissor` — clear, mask, viewport, scissor, depth, and stencil assertions match ES 3.0; the ANGLE viewport deviation is narrowly matched and described.
- `es20-copy-and-read-pixels` — pack layout and read/copy behavior are checked against source pixels; undefined out-of-bounds values and padding bytes are not asserted.
- `es20-cube-map` — Table 3.21 mapping, completeness, and defined errors use non-boundary probes; the README excludes major-axis ties and texel boundaries.
- `es20-culling-front-face` — facing and culling follow window-space signed area; point/line behavior and raster probes avoid unsupported coverage assumptions.
- `es20-depth-test` — fixed-function depth rules and state are checked; the `gl_FragDepth` deviation is restricted to radeonsi and documented.
- `es20-framebuffer-objects` — completeness, attachment queries, pixel results, lifecycle, and defined errors are covered; the initial renderbuffer deviation is ANGLE-only.
- `es20-indexed-drawing` — index selection, buffer mutation, and draw results have observable checks and negative controls.
- `es20-primitive-topology` — topology and supported point/line sizes are checked while implementation-dependent line/edge pixels are excluded.
- `es20-shader-compilation` — compile/link status, deletion, validation, and precision checks are observable; ANGLE’s validation-status deviation is narrow.
- `es20-state-queries-errors` — state/error checks and dashboard outcomes are non-vacuous; the unmapped-buffer deviation matches the documented radeonsi case.
- `es20-stencil-test` — the CPU stencil model checks all probe values; unsupported framebuffer capability is handled as a skip.
- `es20-transformations-camera` — matrix known answers, clipping, depth, and pixel comparisons use independent CPU references and exclude ambiguous edge/depth pixels.
- `es20-uniforms` — uploaded uniform values are verified by rendered output and readback, with a negative control.
- `es20-vertex-attributes` — array formats, conversions, VAO state, and pixels are checked; observed Mesa error-side effects are notes rather than hard expectations.
